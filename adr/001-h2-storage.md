# Хранение сцен во встроенной базе H2, изображения карт — отдельной таблицей

## Контекст и постановка задачи

💬 Приложение «Tabletop Canvas» должно сохранять сцены (карта, сетка, токены, туман) на сервере и открывать их при следующей игре. Карта может весить до 20 МБ, а автосохранение выполняется каждые 30 секунд, поэтому способ хранения влияет и на скорость записи, и на удобство запуска. Бизнес-требование BR-05 и цель BG-5 требуют, чтобы подготовленную сцену можно было использовать повторно без потери карты, токенов и тумана. Требование REQ-FUNC-007 задаёт формат (JSON с версией схемы), проверку при загрузке и автосохранение, а REQ-CON-012 — запуск командой `docker compose up --build` без ручных шагов.

➥ Где и в каком виде хранить сцены и изображения карт, чтобы выполнить REQ-FUNC-007 и REQ-CON-012 и не копировать большое изображение при каждом автосохранении?

## Драйверы решения

* **BR-05 / BG-5 (Must):** сцена сохраняется и восстанавливается без потерь.
* **REQ-FUNC-007 (Test):** JSON с полем `schemaVersion`, проверка структуры и версии при загрузке, автосохранение каждые 30 с.
* **REQ-FUNC-001 (Test):** карта до 20 МБ и 8192 px.
* **REQ-CON-012 (Inspection / Demonstration):** запуск одной командой, без установки СУБД вручную.
* **REQ-REL-010 (Test):** повреждённые данные не должны приводить к аварийному завершению.
* **Простота учебной версии:** один пользователь, один компьютер, без учётных записей.

## Рассмотренные варианты

* Встроенная база H2 (файл на томе Docker): сцена как JSON в одной таблице, карты в отдельной таблице
* PostgreSQL в отдельном контейнере
* Файлы JSON и изображений на диске сервера

## Итог решения

➥ Выбран вариант **«Встроенная база H2: сцена как JSON в таблице `scene`, изображение карты в таблице `map_image`»**, потому что он не требует отдельного сервера (REQ-CON-012), даёт транзакционную запись сцены и позволяет не копировать изображение при автосохранении (REQ-FUNC-007).

### Последствия

* Хорошо, потому что `docker compose up --build` поднимает приложение без отдельной СУБД.
* Хорошо, потому что запись сцены (JSON) остаётся небольшой, а автосохранение хранит одну запись и ссылку на уже загруженную карту.
* Хорошо, потому что структура и версия JSON проверяются в одном месте при записи и загрузке (REQ-FUNC-007, REQ-REL-010).
* Плохо, потому что H2 в файле рассчитана на одного пользователя и не подходит для игры нескольких пользователей с общими сценами (она исключена п. 2.3 SRS).
* Плохо, потому что изображения карт накапливаются в базе — требуется очистка неиспользуемых карт.
* Нейтрально, потому что доступ к базе идёт через интерфейс `SceneRepository`, поэтому замена H2 на другую СУБД не затронет ядро.

### Подтверждение

➥ Соответствие решению проверяется тестом `tests/scene_save.md` (REQ-FUNC-007): сохранённая сцена открывается без потерь; повреждённый JSON отклоняется с сообщением; после закрытия и открытия вкладки предлагается восстановить автосохранение. Дополнительно — проверка запуска `docker compose up --build` (REQ-CON-012) и code review `H2SceneRepository`.

## Плюсы и минусы вариантов

### Встроенная база H2: сцена как JSON, карта в отдельной таблице

Таблицы `scene` (`id`, `name`, `schema_version`, `data`, `map_id`, `autosave`, `updated_at`) и `map_image` (`id`, `mime`, `width`, `height`, `content`); файл базы на томе Docker.

* Хорошо, потому что не нужен отдельный контейнер и настройка.
* Хорошо, потому что автосохранение не копирует карту.
* Нейтрально, потому что требует миграций при изменении схемы JSON (поле `schemaVersion`).
* Плохо, потому что не рассчитана на параллельную работу многих пользователей.

### PostgreSQL в отдельном контейнере

Полноценная СУБД, подключение из приложения по сети Docker.

* Хорошо, потому что подходит для многопользовательской работы и больших объёмов.
* Плохо, потому что усложняет запуск и конфигурацию (REQ-CON-012).
* Плохо, потому что избыточна для однопользовательской учебной версии.

### Файлы JSON и изображений на диске сервера

Каждая сцена — отдельный файл, карты — рядом.

* Хорошо, потому что самое простое решение.
* Плохо, потому что запись файла не атомарна: сбой во время автосохранения может повредить сцену (REQ-REL-010).
* Плохо, потому что нужно самостоятельно решать вопросы имён, блокировок и очистки.

## Дополнительная информация

➥ Решение согласовано с заказчиком (преподавателем) в рамках согласования границ версии 1.0. Ссылки: REQ-FUNC-001, REQ-FUNC-007, REQ-REL-010, REQ-CON-012, BR-05, BG-5. Решение подлежит пересмотру, если появятся учётные записи или игра с нескольких устройств (OQ-4) — тогда потребуется СУБД с поддержкой параллельной работы.
